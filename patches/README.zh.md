# DSH 补丁

[English](README.md) | 中文

## 源码归属

父仓库 Gitlink 选择官方 DSH 基线。`series.json` 按应用顺序列出补丁文件及交付所需的 DSH 包脚本。补丁和检查都为空表示上游未被修改。非空补丁集必须明确登记检查，并依据子模块规则审查其充分性。

补丁文件是定制内容的持久来源。在执行 `pnpm run setup` 前导出需要保留的修改；初始化重置 DSH 已跟踪变更并移除未忽略的未跟踪文件，不清理已忽略的凭据、依赖或父仓库运行数据。不要在受管 checkout 中存放独立工作。

## 清单格式

```json
{
  "version": 1,
  "patches": ["0001-extension.patch"],
  "checks": [{ "script": "test", "args": ["-t", "extension"] }]
}
```

示例说明序列化格式，不代表它足以验证任意补丁。脚本名必须存在于补丁应用后的 DSH 包清单中。参数数组不经 shell 拼接。不要将修改预期输出的命令登记为验证。DSH 所需测试、文档和 Note 保留在补丁中；仅当存在独立的主库决定时才需要父仓库 Note。

按需生成包含二进制数据的 Git 补丁。补丁路径限定在 DSH 中；符号链接祖先路径和外部 worktree 会被拒绝。应用使用 Git index，遇错即停，不使用三方合并。失败会恢复上游基线并阻止安装。

## 验证与更新

`pnpm check:patches` 重建临时 checkout，将有效源码与实际子模块比较，拒绝未登记文件，在 DSH 内运行登记的检查，再次比较源码。它允许补丁定义的修改，不要求工作树为空。已忽略的构建和运行文件不属于源码比较范围。

依据固定版本的 DSH 规则选择测试，命令执行器不推断这些义务。[开发指南](../docs/development.zh.md)说明完整升级步骤。实际执行的检查写入交付证据，不重复抄写 DSH 规则。
