# Agent Note: Playbook 命名与故事模式需求

Status: implemented

[English](2026-09-24-playbook-and-story-mode.md) | 中文

## 问题

将可复用的创作内容称为 story 或剧本，容易让人以为完整剧情已经预先写好。PaperMoon 的内容主要提供背景、开场和互动机制。产品也需要为章节式体验保留明确的名称，并在实现前记录需求。

## 决定

中英文均使用 Playbook 指称创作内容。存储、核心、编译器、编辑器、工具和工作区包，以及它们的接口和调用方，统一使用这个名称。Story 留给故事模式，英文名为 Story Mode。Performance 继续表示一次实际互动及其分支。[架构文档](../../../../docs/architecture.zh.md)维护这些职责。

本次更新[上下文拼装决定](2026-09-17-context-composition.zh.md)记录的格式边界。更名不兼容旧接口，不提供别名或数据迁移。新的默认路径和格式身份将新内容与原有 story 数据分开。[当前格式决定](../simplification/2026-09-25-current-format-only.zh.md)移除了产品格式版本管理与历史格式处理。[开发指南](../../../../docs/development.zh.md#冻结修订数据)维护当前数据规则及重新开始的操作说明。

[故事模式目录](../../../../docs/story-mode/README.zh.md)为每个小节保存独立 Markdown 文档，作为产品需求，其中包括影响体验的 UI 与引导。共用体验要求集中维护。工程与交付继续沿用现有流程。所有已实现章节须能在当前版本从头完成，这不承诺旧练习存档能够继续使用。

需求也维护产品文本及翻译原文。此前只描述提示的用途，没有给出措辞，留下了实现时自行编写的空间，固定示例回复也未明确。[文本依据规则](../../../../docs/story-mode/README.zh.md#文本依据)要求先讨论并记录原文，再实现或修改。共用文本集中维护，章节内容由章节文档负责。原样复用的 DSH 控件及真实运行时数据注明来源，自行编写的模板和故事模式异常提示则给出明确措辞。确认的文本已记录为双语原文，不能仅因出现在代码中就视为需求依据。

故事模式插件负责章节定义、进度编排、专用 UI、引导及包含 Playbook 在内的预置内容。通用机制仍由其他包实现，让普通使用也能受益于章节驱动的开发。这项决定确立命名与需求记录方式。[分层与实现决策](2026-09-25-story-mode-layers.zh.md)记录后续的运行时边界。

[第零章：hello world](../../../../docs/story-mode/00/README.zh.md)记录确认的体验需求。原 DeepSeek API Key 标题占位文档先改为检查模型配置小节，其需求现调整为在主体展示[故事模式介绍](../../../../docs/story-mode/00/01-introduction.zh.md)，操作引导保留在侧栏。已有可用配置时强制查看并无准备价值，因此需求改为根据是否存在任意配置齐备的模型决定能否继续，不替用户选择模型，也不发送测试请求。共用要求仍由目录入口文档维护。

本章先用预置示例介绍轨迹查看，再让用户检查真实练习，便于在请求模型前熟悉同一种交互。故事模式提供示例和引导，通用轨迹读取与展示仍由其他包负责。示例锁定输入，两种对话共用简短的系统提示词，便于用户对照请求上下文。练习让用户选择模型，原有 effort 约束由[effort 提示决定](../simplification/2026-09-25-story-mode-effort-guidance.zh.md)替代；提示词原文和具体交互规则由章节文档维护。

章节需求将学习进度与继续对话分开。首次成功回复确定待查看的轨迹，后续消息仍通过原生对话体验发送，完成本章后也可继续。固定查看目标可让用户继续探索，后续请求失败也不会丢失进度。

## 考虑过的替代方案

继续用 story 或剧本指称创作内容，会保留剧情已经写好的误解，也占用了故事模式需要的名称。Scenario 在目标中文界面中不够自然。Lorebook 对 SillyTavern 用户较熟悉，但容易让人沿用既有条目式概念。Playbook 能容纳创作中的运行机制，也保留了独立的产品含义。

只修改界面文字会让包名与 API 术语继续冲突。兼容别名和迁移会保留旧名称，并增加存储、产物与会话处理。本次范围选择新格式，保留旧文件但不支持读取。

将章节变成新的开发流程，会重复现有工程规则。Markdown 体验需求提供产品方向，实现决策继续由 Agent Notes 维护。

直接将实现文本当作需求，会保留未经审阅的措辞。逐字抄录未改动的 DSH 标签会重复上游职责，而将全部现有章节文本留待以后讨论，会留下当前缺口。本次边界选择补齐已确认的章节原文，并记录复用控件和运行时数据来源。

## 影响

调用方与创作程序一起采用新名称。现有数据不能通过新接口继续使用，也不会被自动改写。双语文档、示例和检查随更名更新，不增加章节文档豁免。后续章节可以调整架构，同时保留此前已实现章节的预期体验。
