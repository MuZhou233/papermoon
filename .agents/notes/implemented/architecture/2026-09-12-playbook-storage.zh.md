# Agent Note: Playbook 归属与不可变修订版本复用

Status: implemented

[English](2026-09-12-playbook-storage.md) | 中文

## 问题

个人创作可能在一个项目中维护无关 Playbook，也可能保留几份候选副本。副本需要独立的当前内容和后续历史，已经提交的修订版本则必须保持不变。代码与多语言文案需要共同提交修订版本，存储不能因此依赖任一业务结构。

## 决定

[存储模块](../../../../plugins/playbook-storage/README.zh.md)管理项目、Playbook、每份 Playbook 独有的可变草稿、共享的不可变修订版本、各自的历史目录，以及与目录归属关联的发布记录。复制时复制草稿值和选定的目录引用，复用完整的不可变修订版本。溯源资料不产生同步、合并或保留要求。

每个顶层 KV 条目占一行。草稿提交在同一事务中将值复制到修订版本条目并追加历史。数据库侧比较在一致的读取视图中返回变化的键及两侧值，文本 diff 留给调用方。每次修订版本都有完整内容，不使用差量链，也不对独立提交去重。

主库独立维护 SQLite 数据库，使用 Node 内置驱动。DSH 存储接口提供单条记录的原子操作，不能直接覆盖修订版本、正文和历史归属的共同提交，因此这些 SQL 事务由核心维护。薄 Cordis 适配器注册服务，不将 DSH 类型引入核心。服务注销和连接释放都交给同一个生成器 effect，确保依赖清理结束后再关闭数据库。

## 考虑过的替代方案

为每份新 Playbook 复制全部历史正文，会重复保存数据中最大的不可变部分。共享修订版本能够保留独立编辑，同时省去这部分复制。

将整份 Playbook 内容和历史放进一条 KV 记录可以使用现有 DSH 接口，但每次修改都要重写整个聚合。每个修订版本存一份完整 JSON 比条目表简单，不过按键编辑草稿和数据库侧筛选变化值更适合独立条目行。

将草稿直接转为修订版本，还需要建立下一份草稿或引入写时复制。分别保存可变条目和不可变修订版本条目，可以明确表达提交及继续编辑。

内容哈希、压缩、差量存储和自动合并算法尚无明确需求，却会增加维护工作。按项目拆分数据库会让跨项目复制和原子操作更复杂。当前单连接服务不需要 WAL，DELETE 日志配合 EXTRA 同步优先保证本地写入持久性。

## 影响

新修订版本复制完整的当前内容，普通保存只改写草稿条目。复制历史只增加引用，不复制修订版本正文。最后一个历史引用删除后，修订版本可以被回收，即使溯源资料仍提及它；调用方需要处理历史目标已不存在的情况。

存储校验应用身份、声明的表结构和数据完整性。模块不包含编译器、审核流程、模型或会话绑定，也没有 UI。[人工编辑器](2026-09-12-manual-playbook-editor.zh.md)通过产品配置挂载本服务，这项存储接入无需修改 DSH 存储。公共 API 按主仓库标准维护，实际 Cordis 兼容性通过已构建宿主产物单独检查，主库检查不需要子模块。
